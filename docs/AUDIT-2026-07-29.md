# Project Audit — `simon` (repo `multichat`)

**Date:** 2026-07-29
**Scope:** Full repository at `main` (`2cca5da`), all 14 Rust source files (3,451 lines) and all 24 docs.
**Predecessor:** `docs/AUDIT.md` audited `9a51fc6` and is marked remediated by `61ce52c`. This document audits the tree *after* that remediation.

**Method — this audit ran the code.** Unlike `docs/AUDIT.md`, which could not build, a
toolchain is present. Every Tier 1 finding below was reproduced against the running
release binary, not inferred from reading. Commands and observed output are quoted inline
so each can be re-run.

---

## Headline

The remediation in `61ce52c` did what it claimed for the chat path: input reaches a model,
provider routing is correct, and the audit chain persists. The build claims in `README.md`
are all true — 65 tests pass, `clippy -D warnings` and `fmt --check` are clean, and
`cargo audit` is clean across 388 dependencies.

The problem is that `README.md` § "Security posture" is presented as "the source of truth"
for what exists, and four of its claims do not hold against the running binary:

1. **The encrypted vault is unreachable.** `src/vault.rs` — 413 lines, the second-largest
   module — has **zero call sites**. No CLI command touches it; no `vault.enc` is ever
   created. It is listed under **Implemented**.
2. **`--classified` is not an air gap.** It permits a *remote* Ollama host, verified by
   pointing `simon models --classified` at another machine and watching the request land.
3. **`--classified` does not stop an environment proxy** from carrying "local" traffic off
   the machine.
4. **The audit log is not tamper-evident against tail truncation.** Deleting the last N
   entries leaves `simon audit` reporting success.

This is the same defect class `docs/AUDIT.md` identified — *shipped modules with no
callers, while the docs declare them working*. It was fixed for the providers, the
orchestrator, and the audit log. It was **not** fixed for the vault, and the README was
rewritten to assert the vault works.

# Tier 1 — Broken, or claims something it does not do

### 1.1 The encrypted vault is dead code, but documented as implemented

- **Test:** 6.1 / 9.2
- **Evidence:**
  - `src/main.rs:18` — `pub mod vault;` is the *only* reference to the module.
  - Every `Vault` token outside `src/vault.rs`:
    ```sh
    $ grep -rn 'Vault' src/ --include=*.rs | grep -v '^src/vault.rs'
    (no output)
    ```
  - `src/config.rs:48` builds `vault_file: data_dir.join("vault.enc")`; the only other
    mention of `vault_file` is an assertion in a unit test (`src/config.rs:274`). Nothing
    reads or writes it.
  - `src/main.rs:43-63` — the CLI exposes exactly `Chat`, `Auth`, `Models`, `Audit`. None
    unlocks, creates, or saves a vault.
  - Runtime: after multiple `simon chat` and `simon models` sessions against a scratch
    `SIMON_DATA_DIR`, the directory contains `audit.log`, `config.json`, `skills/` — and
    **no `vault.enc`**.
- **Defect:** `README.md` lists under **Implemented**: *"Encrypted vault — AES-256-GCM,
  Argon2id key derivation, salt persisted in the file header and bound as authenticated
  data. Self-destructs after 5 consecutive wrong passwords or 24 hours idle."* No code path
  in the shipped binary can reach any of it.
- **Failure:** A user reads the Security posture table, concludes secrets are held in an
  encrypted at-rest vault with a wipe policy, and stores keys accordingly. In reality API
  keys live only in the OS keyring (which *is* real — see Clean), and the vault's
  self-destruct, idle-timeout, and Argon2id protections apply to nothing. The feature is
  untestable in production because it cannot be invoked.

> The vault's *internals* are largely sound (AAD binding, Argon2id parameters, per-write
> nonce — all verified, see Clean). This is a wiring defect, not a crypto defect. Findings
> 3.1 and 3.2 below are latent bugs to fix **before** wiring it up.

### 1.2 `--classified` accepts a remote Ollama host — proven end to end

- **Test:** 2.1 / 6.3
- **Evidence:**
  - `src/orchestrator.rs:66-77` — Ollama discovery runs **before and outside** the gate;
    the `if !classified` block that suppresses cloud and local-binary providers begins at
    `src/orchestrator.rs:79`.
  - `src/providers/ollama.rs:119-121` — `fn is_remote(&self) -> bool { false }`, a
    compile-time constant that ignores `self.host`.
  - `src/config.rs:135` — `pub ollama_host: String`, deserialized from user-writable
    `config.json`. `src/config.rs:154` sets a loopback *default* only. No validation exists:
    ```sh
    $ grep -rn 'is_loopback\|loopback' src/
    (only the default literal and test fixtures)
    ```
  - `src/orchestrator.rs:138-146` — the classified gate consults `is_remote()` on the
    **primary provider only**, which for Ollama is always `false`.
- **Reproduction (run during this audit).** A stub Ollama was bound to this host's LAN
  address `192.168.1.192` (not loopback), and `config.json` set to
  `{"ollama_host":"http://192.168.1.192:11434"}`:
  ```
  $ ./target/release/simon models --classified
  [security] seccomp sandboxing is not implemented
  Reachable models:
    * ollama:pwned-model:latest
  ```
  A full chat turn was then driven under `--classified`, typing `TOP-SECRET-PAYLOAD-98765`.
  The remote listener's log — the prompt itself left the machine:
  ```
  EXFIL-GET  /api/tags
  EXFIL-POST /api/generate BODY={"model":"pwned-model:latest",
    "prompt":"TOP-SECRET-PAYLOAD-98765","stream":false,
    "system":"## SWARM LEDGER (shared blackboard)\n\n### Available models\n
     - ollama:pwned-model:latest\n\n### Resource budgets\n… ### Delegation protocol\n…"}
  ```
  The user's prompt **and** the entire system prompt were transmitted off-host while the
  air-gap flag was set.
- **Defect:** `--classified` is documented as *"refuses any provider whose traffic leaves
  the machine"* and as *"an actual air gap rather than a flag that is parsed and ignored"*
  (`src/orchestrator.rs:55-57`). A one-line edit to `config.json` defeats it.
- **Failure:** An operator runs `simon chat --classified` believing no data can leave the
  host. Because the selected provider reports `is_remote() == false`, the chat proceeds and
  every prompt — plus the swarm ledger embedded in the system prompt — is POSTed to
  `http://192.168.1.192:11434/api/generate` (`src/providers/ollama.rs:63`) on a different
  machine. Both legs are runtime-proven above.

### 1.3 An environment proxy captures loopback traffic, including under `--classified`

- **Test:** 2.1 / 6.3
- **Evidence:** `src/providers/mod.rs:114-120` — `http_client()` builds a `reqwest::Client`
  with no `.no_proxy()` and no loopback exemption. reqwest honours `ALL_PROXY` by default
  and exempts only hosts listed in `NO_PROXY`; nothing in the codebase sets `NO_PROXY`, and
  the `classified` flag is not consulted when constructing the client.
- **Reproduction (run during this audit).** With a real Ollama on `127.0.0.1:11434` and a
  *dead* SOCKS5 port as the proxy — if loopback were exempt, this would succeed:
  ```
  $ ./target/release/simon models                     # baseline, no proxy
  Reachable models:
    * ollama:llama3.2:3b

  $ ALL_PROXY=socks5://127.0.0.1:1 ./target/release/simon models
  [discovery] Ollama unavailable: could not reach the Ollama daemon at http://127.0.0.1:11434/api/tags
  Error: no models are reachable.

  $ ALL_PROXY=socks5://127.0.0.1:1 ./target/release/simon models --classified
  [discovery] Ollama unavailable: could not reach the Ollama daemon at http://127.0.0.1:11434/api/tags
  Error: no models are reachable. Classified mode permits local models only.
  ```
  The loopback request fails *because it was routed to the proxy* — proving it is proxied,
  and that `--classified` does not change this.
- **Defect:** `--classified` does not neutralise proxy configuration, so traffic to a
  genuinely local model can be redirected off-machine by an environment variable.
- **Failure:** `ALL_PROXY` is set in the user's shell profile (a corporate MITM proxy, a
  leftover from unrelated work, or an attacker who can write a dotfile). With a *live*
  proxy instead of the dead one above, `simon chat --classified` against a loopback Ollama
  sends every prompt through that proxy host. The air-gap guarantee is silently void, with
  no warning printed.

### 1.4 Audit log tail truncation is silently accepted

- **Test:** 14.2 / 14.3
- **Evidence:** `src/audit.rs:128-166` — `verify()` walks forward from `GENESIS` over
  whatever lines the file currently holds. There is no stored expected chain head, no entry
  count, and no external anchor, so a prefix of a valid chain is itself a valid chain.
  `read_last_mac()` (`src/audit.rs:170-187`) then adopts the new last line as the head and
  keeps appending as if nothing happened.
- **Reproduction (run during this audit)** on a genuine 4-entry log produced by real
  sessions:
  ```
  ATTACK 1 — delete the last 2 entries:
    $ head -2 audit.log.bak > audit.log && simon audit
    Audit chain verified: 2 entries intact.          <-- passes

  ATTACK 2 — delete the first entry:
    $ tail -3 audit.log.bak > audit.log && simon audit
    Error: audit chain broken at entry 1: expected prev 0000...0000, found 276d4639...

  CONTROL — modify an entry in place:
    $ sed -i 's/pwned-model:latest/innocent/' audit.log && simon audit
    Error: audit entry 1 has been modified (MAC mismatch)
  ```
- **Defect:** `README.md` claims a *"tamper-evident audit log"* and that *"`simon audit`
  verifies the whole file."* It verifies the file that is *present*; it cannot know entries
  were removed from the end.
- **Failure:** An operator covering their tracks — or malware after the fact — deletes the
  trailing entries covering an incident. `simon audit` prints "verified" and the session
  continues chaining from the truncated head. Checklist 14.2 requires the system to reject
  the deletion and alert; it does neither.

> Precise boundary, established by the control tests above: **in-place modification and
> head/middle deletion are correctly detected.** The MAC construction is sound (see Clean).
> Tail truncation is the single blind spot, and it is the one an attacker would choose.

# Tier 2 — Security / policy weakness

### 2.1 The CI `unsafe` boundary check is bypassable by the outer attribute form

- **Test:** 1.2 / 7.3
- **Evidence:** `.github/workflows/ci.yml:53` greps a **fixed string**, the *inner*
  attribute only:
  ```sh
  offenders=$(grep -rlnF '#![allow(unsafe_code)]' src/ | grep -v '^src/security.rs$' || true)
  ```
  Rust's `deny` (used at `src/main.rs:7`, deliberately, since `forbid` is not overridable)
  can equally be overridden by the **outer** form `#[allow(unsafe_code)]` on a module,
  function, or block — which that grep does not match.
- **Verified empirically during this audit.** A scratch crate reproducing the project's
  exact lint posture compiles clean:
  ```rust
  #![deny(unsafe_code)]
  #[allow(unsafe_code)]              // outer form — CI never looks for this
  fn sneaky() -> i32 { let x = 5i32; let p = &x as *const i32; unsafe { *p } }
  ```
  ```
  $ cargo build
      Finished `dev` profile [unoptimized + debuginfo] target(s)
  ```
- **Defect:** The job is described as *"the missing half of the guarantee"* backing the
  README claim *"`unsafe` confined to one file … enforced by a CI job."* Half the ways to
  override the lint are unchecked.
- **Failure:** A contributor (or a model writing a patch) adds `#[allow(unsafe_code)]` above
  a function in `src/providers/cloud.rs` and writes an unsound `unsafe` block. `cargo build`,
  `clippy`, and the `unsafe-boundary` job all pass, and the stated invariant is broken with
  no signal. **The current tree is clean** — the grep for the outer form returns nothing —
  so this is a gap in the guard, not an active breach.
- **Fix:** key the check on the **lint name**, not the attribute's literal shape. Matching
  `'#!?\[allow\(unsafe_code\)\]'` still misses the realistic multi-lint case
  `#[allow(dead_code, unsafe_code)]`, as well as `#[cfg_attr(all(), allow(unsafe_code))]`
  and whitespace variants. Prefer `grep -rlnE 'allow\([^)]*unsafe_code' src/`.

### 2.2 Per-allocation memory locking is dead code in the shipped binary

- **Test:** 9.2
- **Evidence:** `LockedBuffer` (`src/security.rs:88-116`) is referenced only by
  `src/vault.rs:36,109,114` and its own unit test:
  ```sh
  $ grep -rn 'LockedBuffer' src/ --include=*.rs
  src/security.rs:57,88,93,109,166   # definition + doc comment + own test
  src/vault.rs:36,109,114            # the only consumer
  ```
  Since the vault is unreachable (1.1), so is every `mlock`/`VirtualLock`/zeroize-on-drop
  call built on it.
- **Defect:** README lists under **Implemented**: *"Memory locking — `mlockall` on Linux;
  **per-allocation `mlock`/`VirtualLock` for derived key material**, zeroized on drop."*
  The first clause is true and wired (`src/main.rs:72` → `src/security.rs:35-46`, observed
  running). The second clause protects no live allocation.
- **Failure:** A reader concludes derived key material is individually locked and wiped on
  both Unix and Windows. In the shipped binary no such allocation exists; only the
  process-wide Linux `mlockall` is in force, and it is absent on macOS and Windows — exactly
  the platforms the per-allocation path was meant to cover.

### 2.3 Audit entries carry no model or configuration identity

- **Test:** 14.1
- **Evidence:** `src/audit.rs:28-37` — `AuditEntry { ts, action, details, prev, mac }`. The
  only free-form field is `details: String`. Observed entry from a real session:
  ```json
  {"ts":1785332466,"action":"session.start","details":"primary=ollama:llama3.2:3b","prev":"…","mac":"…"}
  ```
- **Defect:** Policy §14 requires *"high-fidelity metadata (timestamps, model versions,
  configuration IDs)"*. There is a timestamp, but model identity is prose inside `details`
  by convention, and no field records a model *version* or config ID at all.
- **Failure:** Asked "which model version handled this request," the log cannot answer.
  `primary=ollama:llama3.2:3b` names a tag that mutates when the tag is repulled — the
  digest is available from `/api/tags` at discovery time and is not recorded.

### 2.4 WORM is detection-only, and only when a human asks

- **Test:** 14.2
- **Evidence:** `verify()` runs solely from `simon audit` (`src/main.rs:88-89,146-150`).
  There is no filesystem immutability, no append-only mode, no periodic check, no alert
  path. The log is an ordinary `0600` file any process running as the user can rewrite.
- **Defect:** Checklist 14.2 requires the system to *reject* the write and *raise an alert*.
  It does neither; it can only report, later, if invoked.
- **Failure:** Combined with 1.4, an attacker truncates the tail and no alert exists to
  fire even in principle. *(README's "Known limits" honestly discloses the related MAC-vs-
  signature gap, checklist 14.4 — that one is documented, this one is not.)*

# Tier 3 — Defects

*3.1 and 3.2 are latent: they are unreachable today because of 1.1, and must be fixed
before the vault is wired up.*

### 3.1 A failed attempt-counter write silently grants unlimited guesses

- **Evidence:** `src/vault.rs:252-254`:
  ```rust
  Err(_) => {
      header.attempts = header.attempts.saturating_add(1);
      let _ = self.rewrite_header(&raw, &header);   // <- result discarded
  ```
  `rewrite_header` (`src/vault.rs:268-298`) writes via a temp file plus rename in the vault's
  own directory.
- **Defect:** The counter is incremented *after* the failed decrypt and persisted on a
  best-effort basis, with the error dropped. If the write cannot complete, the attempt is
  never charged and no error surfaces.
- **Failure:** An attacker who can make that write fail — mount the directory read-only,
  exhaust its inodes, or hold the rename — guesses indefinitely against a vault documented
  as self-destructing after 5 tries. Because `attempts` is re-read from disk by each fresh
  process, the reported `remaining` count stays *constant* across attempts rather than
  counting down. A crash between decrypt and rename has the same effect. *(README already discloses the weaker file-copy reset; this is a
  distinct path that needs no copy.)*
- **Fix:** reserve the attempt on disk *before* calling `decrypt`, and propagate the write
  error instead of discarding it.

### 3.2 The AES round-key schedule is neither locked nor zeroized

- **Evidence:** `src/vault.rs:235-237` derives the key into a `LockedBuffer`, then
  `Aes256Gcm::new(...)` copies it into the cipher's own expanded key schedule — an ordinary
  heap/stack allocation. `Cargo.toml:31` declares `aes-gcm = "0.10"` with no features; the
  crate exposes an optional `zeroize` dependency that is not enabled.
- **Defect:** README claims derived key material is *"zeroized on drop."* The `LockedBuffer`
  copy is; the round-key expansion of the same key is not, and outlives it until `cipher`
  drops without wiping.
- **Failure:** A core dump, swap page, or hibernation image captured after a vault unlock
  yields the AES-256 key from the leftover round keys, despite the "protected" copy having
  been correctly wiped.
- **Fix:** `aes-gcm = { version = "0.10", features = ["zeroize"] }`.

### 3.3 Derived key is briefly unlocked between derivation and `mlock`

- **Evidence:** `src/vault.rs:109-115` — `hash_password_into` writes the finished key into a
  plain `vec![0u8; KEY_LEN]`, and only the subsequent `LockedBuffer::new(key)` calls `mlock`.
- **Defect:** A window exists in which the plaintext key sits in ordinary swappable memory.
- **Failure:** A swap-out inside that window leaves the key in the swap file on a host
  without encrypted swap. Narrow, but avoidable by locking the buffer before deriving into it.

### 3.4 TOCTOU between skills-path validation and open

- **Evidence:** `src/skills.rs:57-69` canonicalizes and prefix-checks; `src/skills.rs:72-85`
  then re-resolves the same path by name for `fs::metadata` and `fs::read_to_string`.
- **Defect:** Validation and use are separate name-based resolutions, so a component can be
  swapped between them. Canonicalizing does not close this; holding a descriptor would.
- **Failure:** A local process with write access to the skills tree races a symlink swap and
  causes a read outside the root, against the claim that *"symlinks escaping the root are
  all rejected."* Low severity — the skills directory is `0700` user-owned and is not
  reachable from model-generated text.

# Checked and clean

These were tested and hold. Several are places an audit would expect to find a problem.

**Build and quality claims — all verified by running them:**
- `cargo test --all-targets` → **65 passed, 0 failed**, matching the README exactly.
- `cargo clippy --all-targets -- -D warnings` → clean.
- `cargo fmt --all -- --check` → clean.
- `cargo audit` → **no vulnerabilities across 388 dependencies** (`rc=0`, 1173 advisories
  loaded, no advisory list emitted). This closes the explicitly-open item from
  `docs/AUDIT.md`, which could not run it for lack of a toolchain.
- CI (`.github/workflows/ci.yml`) genuinely runs fmt, clippy, test, release build across
  Linux/Windows/macOS, plus `cargo-audit` (job at `:81`) and the doc-length check. The
  README's "CI runs all of the above" is accurate.

**Audit chain (the parts that work):** the MAC covers the entry's *own* payload, not merely
the previous hash — `MacPayload { prev, ts, action, details }` (`src/audit.rs:42-48`),
recomputed per entry in `verify()`. The classic "chains the hash but not the content" flaw
is **not** present, and in-place edits and head deletion are both rejected (proven above).
Chain-head recovery across restarts works. Keyring failures fail closed rather than skipping
verification (`src/config.rs:199-218`).

**Vault internals (sound, just unreachable):** the salt is genuinely bound as AEAD
associated data on both save and load (`src/vault.rs:74-84,175,230`), with a passing
tamper test. `Argon2::default()` is Argon2**id** at RFC 9106 parameters (m=19456 KiB, t=2,
p=1) — not a token default. A fresh random nonce is generated per save.

**Provider routing — the `61ce52c` regression is genuinely fixed.** `CloudProvider` branches
on an `Api` enum fixed at construction from hardcoded endpoints (`src/config.rs:103-128`),
never on a provider-name string. Test `anthropic_and_openai_hit_different_urls`
(`src/providers/cloud.rs:220-231`) guards the exact "Anthropic key sent to OpenAI" bug.

**Delegation is not a prompt-injection foothold.** `MAX_DELEGATIONS_PER_TURN = 3` is enforced
by `.take(3)` on a freshly parsed list each turn (`src/orchestrator.rs:22,298`), so no
crafted reply can reset a counter. Sub-agent replies are **not** re-parsed for delegations,
so recursion is genuinely impossible. A model can choose *which pre-registered provider*
receives a delegation but cannot introduce a binary or argv: `LocalBinaryProvider` is
constructed only from `Settings.local_binaries`. Process spawning uses
`Command::new(path).arg(prompt)` — argv only, no shell (`src/providers/local_binary.rs:62-68`).

**Secrets do not leak into argv or logs.** Keys are read from a hidden prompt or stdin
(`src/main.rs:117-125`); no CLI flag accepts one. `CloudProvider` does not derive `Debug`, so
an accidental `{:?}` would fail to compile. Audit entries record labels, char counts, and
task IDs — never prompt text or key material. No hardcoded secret exists in `src/`
(checklist 6.1); the only literal key bytes are `#[cfg(test)]` fixtures.

**`unsafe` soundness.** Every block in `src/security.rs` passes a pointer+length pair from a
live, unresized `Vec` to libc, guards zero length, and never dereferences the raw pointer.
The process-wide `mlockall` path is genuinely wired (`src/main.rs:72`) and `--classified`
correctly escalates a locking failure to a hard startup abort (`src/security.rs:34-70`).

**TUI plumbing.** `src/app.rs` is deliberately I/O-free state (`//! kept free of I/O so it
can be unit-tested`) and carries its own tests, including that backspacing an empty buffer
does not panic. `src/ui/mod.rs:27-50` restores the terminal from an RAII `Drop` guard, so a
panic or an early `?` cannot leave the user in raw mode — confirmed across the pty sessions
run for this audit, all of which exited to a sane terminal.

**Honest disclosure where it counts.** The **Not implemented** list is accurate: seccomp
really is a no-op that announces itself — the binary prints
`[security] seccomp sandboxing is not implemented` on every run, observed in every command
above. `local_binary` really is treated as remote under `--classified`
(`src/providers/local_binary.rs:110-112`), which makes the Ollama exemption in 1.2 the one
place the stated model breaks.

## Recommended order of work

1. **1.2 and 1.3** — `--classified` is the product's headline security control and is
   currently defeatable from a config file or an environment variable. Validate
   `ollama_host` against loopback (or make `is_remote()` a function of the host), move
   discovery inside the gate, apply the gate to delegation targets as well as the primary,
   and set `no_proxy` for loopback destinations under `--classified`.
2. **1.4** — persist the expected entry count and head MAC outside the log (keyring beside
   the MAC key), and have `verify()` reject a short chain.
3. **1.1** — decide the vault's fate. Either wire it to a real command (fixing 3.1–3.3
   first) or delete it and strike the claim. Shipping 413 lines of unreachable security code
   that the README presents as active is the worst of the three options.
4. **2.1** — one-character regex fix; do it while the tree is still clean.
5. **4.1** — bring `README.md` and `docs/progress/22_status.md` back in line with whatever
   1.1–1.3 resolve to.
