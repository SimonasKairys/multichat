**Date:** 2026-07-30
**Scope:** `main` at `9540ace`, focused on the ~1,700 lines added by `8f947c4` and
`9540ace` — the delegation/skills changes and the vault wiring.
**Predecessor:** the 2026-07-29 audit covered `2cca5da`; this document audits the tree
after the two commits that followed it. That audit and its own predecessor (`docs/
AUDIT.md`, covering the initial Rust commit) were removed from the tree as superseded —
both are recoverable at commit `2e7984e`.

**Method — this audit ran the code.** Every Tier 1 finding was reproduced against the
running release binary or a temporary instrumented test, not inferred from reading.
Commands and observed output are quoted inline so each can be re-run.

---

## Headline

The two commits since the last audit closed its single largest finding: **the encrypted
vault is no longer dead code.** `simon chat --vault` constructs an `EncryptedVault`,
`derive_key` runs, and the per-allocation `mlock` of key material executes for the first
time. A dead-code sweep (method in §5) shows zero vault symbols remaining. Finding 1.1 of
the previous audit is resolved, and the README no longer overstates it.

Two of the four previous Tier 1 findings are resolved. **One is still open and was
re-verified at this commit: audit log tail truncation is still silently accepted (§3.3).**

The new findings are not defects in the sense of broken code — the code does what its
comments say. They are consequences of a design change that has not been reasoned about
end to end: **the swarm ledger stopped being a small blackboard of labels and task titles,
and became a carrier for sub-agent output and file contents.** That changes two things
nobody has written down — what leaves the machine (§3.1) and what every call costs
(§3.2).

## 2. What changed structurally

Before `8f947c4`, `SwarmLedger::system_prompt()` emitted model labels, budget strings,
and task descriptions — all short, all authored by the application or by the model that
wrote the delegation line.

It now additionally carries:

- **delegated sub-agent replies**, up to `MAX_RESULT_CHARS` (2,000) each, for up to
  `MAX_RENDERED_TASKS` (20) tasks (`swarm.rs:52,59`)
- **skill file contents**, up to `MAX_SKILL_CONTENT_CHARS` (4,000) each, for up to
  `MAX_LOADED_SKILLS` (3) skills (`swarm.rs:66,72`)

That block is assembled by `Orchestrator::system_prompt()` and passed as the system
prompt to **every** provider call — the primary in `handle_prompt`, and each delegate in
`run_delegations`. The two findings below both follow from that.

## 3. Findings

### 3.1 Skill contents and sub-agent replies now leave the machine — undocumented (Tier 1)

Once a model emits `ACTION: read_skill(notes.md)`, that file's contents sit in the ledger
and are included in the system prompt of every subsequent call for the rest of the
session — including calls to Anthropic, OpenAI, OpenRouter and Groq.

The same is true of delegation results: a *local* Ollama model can be asked to summarise
a private document, and its reply is recorded via `record_result` and then transmitted to
whichever cloud provider is primary on the next turn.

This is a genuine change in data flow. Before these commits, the only user content that
left the machine was the prompt the user typed. Now the contents of local files and the
output of local models do too, without the user doing anything that looks like sending
them.

**Not a bug in the code** — it is exactly what "shared blackboard" implies, and it is what
makes delegation useful. The defect is that **nothing says so.** `README.md` § Skills
describes `read_skill` as loading content "into the ledger" and never states that the
ledger goes to remote providers. The § Security posture section is otherwise scrupulous
about egress (it documents `--classified`, proxy behaviour, and per-vendor key routing).

`--classified` is a complete mitigation — it refuses every remote provider, so nothing
egresses. That is worth saying explicitly in the skills documentation, because it is
currently the only control available.

**Recommended:** document it in § Skills and § Delegation, and note `--classified` as the
mitigation. Consider a per-skill `local_only: true` frontmatter key that refuses to load
the skill when any remote provider is connected — the frontmatter parser already exists.

### 3.2 The system prompt can reach ~13,700 tokens, on every call (Tier 1)

Measured, not estimated. A temporary test built a worst-case ledger at the documented caps
and printed the rendered size:

```
PROBE system_prompt chars = 54818
PROBE approx tokens (chars/4) = 13704
```

(20 tasks each with a 2,000-char result, plus 3 skills each with 4,000 chars of content.
Probe added to `swarm.rs` tests, measured, and removed; `git diff src/swarm.rs` clean
afterwards.)

That block is sent on **every** provider call. With the maximum three delegations in a
turn, one user message produces four calls, each carrying it — roughly **55,000 tokens of
system prompt per turn**, before the user's actual prompt.

The individual caps are all sensibly chosen and well commented. What is missing is that
nobody multiplied them together. Consequences:

- Cost, on metered providers, scales with ledger history rather than with what the user
  typed.
- Latency, on every call including delegations.
- Smaller local models can have their usable context consumed by the blackboard.

There is also **no way to clear the ledger.** Tasks accumulate for the session;
`Command::Reconfigure` calls `ledger.set_roster` but does not reset tasks
(`orchestrator.rs`), so reopening the picker does not help.

**Recommended:** a total character budget for the whole rendered ledger, enforced across
tasks and skills together, rather than per-item caps that compound. Plus a way to drop
loaded skills and completed tasks from the ledger — either a key binding or an
`ACTION: forget_skill(<name>)` counterpart to `read_skill`.

### 3.3 Audit log tail truncation is still silently accepted (Tier 1, carried forward)

Previous finding 1.4, carried forward. This is genuinely unchanged rather than merely
still-reproducible: `src/audit.rs` was untouched by both `8f947c4` and `9540ace`
(`git diff 8f947c4~1..HEAD -- src/audit.rs` is empty), and `verify()` was last modified
in `61ce52c` — the commit the previous audit recorded as its remediation.

Re-verified at `9540ace`:

```
entries: 2
Audit chain verified: 2 entries intact.
after truncating to 1 entry:
Audit chain verified: 1 entries intact.
```

Deleting entries from the end of the log leaves `simon audit` reporting success. The chain
proves each entry follows its predecessor, but nothing anchors the *length* or the *head*,
so removing a suffix produces a shorter, perfectly valid chain.

This matters more now than it did at the previous audit, because the log gained events
worth suppressing: `vault.unlock_failed` records failed unlock attempts, and truncating
the tail erases exactly the evidence of an attack in progress.

**Recommended:** persist the expected entry count and last MAC in the OS keyring
alongside the existing key — the keyring is already the trust anchor, and `AuditLogger`
already reads from it. `verify()` then compares against that anchor and reports a short
chain as tampering.

### 3.4 Loaded skill content is injected verbatim, unlike delegation results (consistency note, not a security finding)

`record_result` deliberately indents multi-line results so a sub-agent cannot forge ledger
bullets:

```rust
let indented = result.replace('\n', "\n    ");
```

`record_skill` has no equivalent. Skill content is rendered raw at `swarm.rs:262`:

```rust
out.push_str(&format!("#### {}\n{}\n", skill.name, skill.content));
```

and the `### Loaded skills` block is emitted **before** `### Delegation protocol`. A skill
file containing its own `### Delegation protocol` heading would appear ahead of the real
one in the system prompt.

**This is not a vulnerability, and it is listed only for consistency.** Skill files are
user-authored local files: anyone who can write one can already put whatever they like
into the prompt, so there is no attacker in the threat model. The module doc calls the
directory "shared", but nothing in this repo actually syncs it or gives it a second
writer. The asymmetry with `record_result` looks unintentional rather than reasoned.

**Recommended:** apply the same indentation for consistency, or add a comment at
`record_skill` explaining why the two are deliberately different. Either resolves the
ambiguity; neither is urgent.

### 3.5 The audit log avoids content everywhere except error paths (Tier 2)

Normal operation deliberately records sizes, not content:

```rust
self.audit.log("prompt.sent", &format!("model={primary_label} chars={}", prompt.len()));
```

Error paths do not follow that rule. `orchestrator.rs:850` logs `error={e}`, and provider
errors embed truncated response bodies (`cloud.rs:120-135`, `cloud.rs:173`) — model output,
in plaintext, in a file the vault exists to avoid needing.

No API key is exposed (keys are request headers, never echoed in responses), so this is
not a credential leak. But it is a content leak into the one file the design otherwise
keeps content out of.

**Recommended:** log an error *class* and length rather than the formatted error, or strip
embedded response bodies before logging.

### 3.6 The vault transcript grows without bound (Tier 2)

`vault_save_after_chat` serialises the entire transcript and re-encrypts it on every clean
exit. Sessions append, so both the plaintext held in memory and the vault file grow
monotonically across the vault's lifetime. Argon2id then runs over an ever-larger payload.

Nothing truncates, rotates, or prunes. A user who runs `--vault` daily for a year has a
year of transcript re-encrypted at every exit.

Flagged by the implementing agent as a known follow-up; recording it here so it is
tracked. **Recommended:** cap retained lines or offer `simon vault prune --before <date>`.

## 4. Not findings

Recorded so a future audit does not re-investigate them:

- **`--classified` + `--vault`** work together; verified end to end (§5). The vault is
  purely local and correctly does not weaken the air gap.
- **Vault self-destruct as data loss** is a real hazard but is now documented prominently
  in § Known limits, including that the idle check runs *before* the password. Working as
  designed and disclosed.
- **Only a clean exit saves.** Documented, with the Argon2id reasoning.
- **Remaining dead-code sweep hits** (`with_key`, `root`, `tasks`/`roster`/
  `loaded_skills`, `is_applied`, `data_dir`) are test-support accessors, not dead product
  code.

## 6. Recommended order of work

1. **§3.1** — document the egress. Cheapest fix here, and it is a correctness claim about
   what the tool does with private data.
2. **§3.3** — anchor the audit chain in the keyring. Carried from the previous audit and
   now guards vault attack evidence.
3. **§3.2** — a whole-ledger budget plus a way to forget. Compounding caps are a real cost
   bug.
4. **§3.5**, **§3.4**, **§3.6** — content in error logs, skill indentation, vault growth.
