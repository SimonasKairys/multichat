## 2. New findings

### 3.1 `cloud.rs::truncate` panics on multi-byte UTF-8 — reproduced (Tier 1)

`src/providers/cloud.rs:147-153`:

```rust
fn truncate(s: &str) -> String {
    const LIMIT: usize = 300;
    if s.len() <= LIMIT {
        s.to_string()
    } else {
        format!("{}…", &s[..LIMIT])   // byte index; panics off a char boundary
    }
}
```

`s.len()` and `&s[..300]` are **byte** operations. If byte 300 falls inside a
multi-byte character, the slice panics. Reproduced with a temporary test in this tree
(one ASCII byte followed by 3-byte `€` chars, so no char boundary lands on 300):

```
thread 'providers::cloud::tests::probe_truncate_multibyte_panics' panicked at
src\providers\cloud.rs:152:26:
end byte index 300 is not a char boundary; it is inside '€' (bytes 298..301 of string)
```

**Reachability.** `truncate` runs on provider-controlled text on every cloud error
path: HTTP error bodies (`send`, `cloud.rs:172-178`) and the response JSON embedded in
"returned no text content" errors (`extract_text`, `cloud.rs:119-124` and `134-139`).
Provider error messages and model output are routinely non-ASCII — a single `’`, `é`,
emoji, or non-Latin text in the wrong 3-byte window is sufficient. No attacker needed;
an ordinary refusal body can do it.

**Impact.** The panic fires inside the orchestrator task
(`tokio::spawn(orchestrator.run(..))`, `main.rs:243`). The task dies, the event channel
closes, and the UI loop exits (`ui/mod.rs:114-116`): the whole chat session ends on a
provider hiccup, and the `session.end` audit entry is never written — an unexplained
hole in the very chain `simon audit` verifies. (The `--vault` save still runs, since
the UI itself returns cleanly.)

**The codebase already knows this rule.** `record_result` (`swarm.rs:145`),
`record_skill` (`swarm.rs:169`), and `summarize_stderr` (`local_binary.rs:114`) all cut
via `char_indices().nth(..)`, each with a comment saying byte-slicing panics, and the
suite carries three regression tests for exactly this class. `cloud.rs::truncate` is
the one truncation that predates the pattern and was never brought in line.

**Recommended:** replace the body with the same `char_indices().nth(LIMIT)` cut and add
the sibling regression test. One function, mechanical fix.

**Resolved in this commit.** `truncate` was replaced by `providers::truncate_error_detail`
(`src/providers/mod.rs`), shared with `ollama.rs` (§3.3), cutting via
`char_indices().nth(MAX_ERROR_DETAIL_CHARS)`. Note the semantic change this carries: the
cap is now 300 **characters**, where the old code compared `s.len()` — 300 *bytes* — so
non-ASCII detail is no longer cut roughly three times shorter than intended.

The regression test was verified to actually catch the bug, not merely to pass: reverting
the helper to the old byte slice reproduces the original panic verbatim
(`end byte index 300 is not a char boundary; it is inside '€' (bytes 298..301)`), and the
helper was restored afterwards. Worth recording because the first version of that test
used a 121-character input — over the old 300-byte limit but under the new 300-char one,
so it exercised no truncation at all and asserted against a value the corrected code
never produces.

### 3.2 `MAX_OUTPUT_BYTES` caps what is kept, not what is buffered (Tier 2)

`src/providers/local_binary.rs:16-17` declares:

```rust
/// Ceiling on captured output, so a runaway child cannot exhaust memory.
const MAX_OUTPUT_BYTES: usize = 1 << 20;
```

But the cap is applied at line 172-173 — **after** `command.output().await` has already
buffered the child's entire stdout (and stderr) into memory. A child that writes
gigabytes quickly, well inside the 300 s timeout, exhausts memory before `truncate` is
reached. The comment claims a protection the code does not provide.

The 300 s timeout bounds duration, not volume; the binary path comes from the user's
own config, so the writer is misconfiguration or a buggy CLI rather than an attacker —
which is exactly the case the comment says it handles.

**Recommended:** either stream the child's stdout through a capped reader (kill the
child once the cap is hit), or reword the comment to say the cap bounds what is
*retained*, with the timeout as the only real runaway control. The first matches what
the constant's name promises.

### 3.3 Ollama error detail is unbounded (Tier 3, consistency)

`src/providers/ollama.rs:83-84` embeds `detail.trim()` — the full response body — into
the error, with no `truncate` at all. That error reaches the transcript
(`Event::Error`) and the audit log via `prompt.failed`/`task.failed` `error={e}`
(`orchestrator.rs:851,937`). Same content-into-audit-log concern as the previous
audit's §3.5, plus an unbounded-size wrinkle its cloud sibling doesn't have. Fixing
§3.1 above with a shared, char-safe `truncate` helper and using it here resolves both
halves at once.

**Resolved in this commit** by that shared helper. Note the scope: this bounds the
*size* of the detail embedded in the error, which is the unbounded-size half. The
content-in-the-audit-log half — the previous audit's §3.5, that `error={e}` writes
model- and provider-controlled text into the log the vault exists to avoid needing —
is untouched and remains open.

### 3.4 `Settings::save` is not atomic (Tier 3)

`config.rs:223-227` writes `config.json` with a bare `fs::write`. The vault module
already has `write_atomically` (temp file + rename, `vault.rs:345-350`) precisely
because a crash mid-write must not truncate the existing file — but the config, which
is rewritten on every picker submit (`ui/mod.rs:153`, `main.rs:217`), gets no such
protection. A crash mid-save leaves a truncated `config.json`, and `Settings::load`
then errors out at startup ("failed to parse …") until the user repairs or deletes the
file by hand. Low probability, but the fix is lifting an existing function.

### 3.5 Audit-key edge cases: malformed keyring entry, concurrent writers (Tier 3)

Two observations on `audit.rs`, recorded so a future audit need not re-derive them:

- `load_or_create_key` (`audit.rs:190-208`): if the keyring returns a value that is
  not 32 bytes of valid hex, a **new** key is silently generated and stored over it.
  Every existing log entry then fails verification as "modified" — misreporting key
  loss as file tampering, and destroying the old key with no warning. A malformed key
  should be an error naming the real cause, not a silent rotation.
- Two concurrent `simon` processes (two chats, or a chat plus `vault destroy`) each
  read the same chain head and append independently; the interleaved file then fails
  `verify()` even though nobody tampered with anything. Single-user CLI, so accepted
  behaviour — but worth a line in the README's audit-log documentation, since the
  failure message ("chain broken") reads as an attack.

### 3.6 Ctrl-modified characters are typed into the input (nit)

`ui/mod.rs:259`: the fall-through arm `KeyCode::Char(c) => app.push_char(c)` ignores
modifiers, so any Ctrl+letter chord without a dedicated handler (Ctrl+A, Ctrl+K, …)
inserts the bare letter into the prompt. Cosmetic; noted because the adjacent arms
(`Ctrl+C`, `Ctrl+O`) do check modifiers.

## 4. Not findings

Recorded so a future audit does not re-investigate:

- **`picker.rs` (new since the 2026-07-29 baseline, lightly covered by prior audits)
  is sound.** State is I/O-free and well tested; unavailable rows cannot be toggled or
  promoted (`toggle`/`set_commander` re-check availability); two transports of one
  vendor share a single `Selection`, so double-ticking is impossible by construction;
  `submit()` refuses an empty selection and falls back to the first enabled connection
  for commander. No defects found.
- **`skills.rs` traversal hardening holds on both call paths.** `read` and
  `read_description` both route through `resolve()`, so the listed-symlink leak the
  code comments describe is genuinely closed, with regression tests.
- **`security.rs`** matches its documentation: the single `unsafe` override, fail-soft
  non-strict path, seccomp honestly reported as absent.
- **Test-count discrepancy explained.** The previous audit recorded 138 passing tests;
  this machine reports 132. The difference is exactly the six `#[cfg(unix)]` tests
  (two each in `orchestrator.rs`, `providers/local_binary.rs`, `skills.rs`), which do
  not compile on Windows. Nothing is failing or missing.
- **Delegation under `--classified` cannot reach a remote sub-agent.** The registry
  re-checks availability for every saved connection at build time
  (`orchestrator.rs:577-585`), not just the primary, so the swarm roster itself is
  air-gapped. Verified in code; matches the previous audit's resolved finding 1.2.
