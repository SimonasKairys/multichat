**Scope:** Incremental audit of everything landed since `docs/AUDIT-2026-08-26.md` — the range `746e914..HEAD`: the ten reproducer fixes (`bae78fc`), the CLI-discovery and dependency-gate hardening (`3c4818a`), the mutation-gap tests (`d9b5a25`), and the token-usage statusline feature (`55c528d`) — plus a dependency advisory scan and repo-hygiene pass over the whole tree.

## Headline

Four defects found and fixed: a quote-tracking regression in the action parser that silently dropped delegations containing an apostrophe (and un-fenced `write_file` blocks, letting stored content execute as actions), Windows CLI discovery preferring npm's unspawnable POSIX shim over the `.cmd` beside it, server-controlled rate-limit header strings flowing unbounded into the status line and every model's system prompt, and two CI dependency-audit scripts that silently passed when the command they audit with failed. Reconciling with the seventeen peer commits that landed mid-audit added two more: a third copy of the parser defect in the field splitter, which both sessions' independent fixes had missed (§2.1), and a peer tree that arrived red on Windows — one clippy error and three failing tests, behind which sat a production defect that broke every proof run in a task copy on this platform (§2.5).

The full gate after the fixes: `cargo fmt` clean, `cargo clippy --all-targets -- -D warnings` clean, **652 tests passed, 0 failed, 0 ignored** (Windows; the unix-only executor and symlink tests raise the count on Linux), `cargo audit` clean over 385 locked dependencies, and `cargo mutants --in-diff` over this audit's own diff at **34 mutants: 30 caught, 4 unviable, 0 missed** (§4.1 tells the story of the one that survived the first sweep).

## 2. Detailed Findings & Reproduction Proofs

### 2.1 `src/swarm.rs`: prose apostrophe silently discards actions and un-fences `write_file` blocks (Tier 1)

- **Introduced by:** `bae78fc` (the escaped-quote handling added for Windows paths brought quote *tracking* with it; at the range base `746e914` the scanner was pure depth counting and parsed these inputs correctly).
- **Defect:** The scanner entered quote mode on **any** `'` or `"` at paren depth ≥ 1. For the preamble's own documented unquoted form — `ACTION: delegate_task(worker, Summarize the user's login flow)` — the apostrophe in `user's` opened a quote that never closed, every remaining character including the closing `)` was consumed by the quote branch, and `action_argument` returned `None`: the delegation vanished with no error and no ledger record. All five action parsers route through this function, so the same held for `read_skill`, `read_file`, `list_files` — and for `write_file`, where a dropped *open* line meant the block was never recognised and its content lines — written to be **stored** — were parsed as actions to **execute**, defeating the documented protection that action-shaped lines inside file content must not run.
- **Proof Tests:**
  - `swarm::tests::reproduction_test_apostrophe_in_unquoted_prose_does_not_swallow_the_action`
  - `swarm::tests::reproduction_test_apostrophe_in_write_file_path_keeps_its_block_fenced`
  - `swarm::tests::an_unterminated_quoted_argument_still_parses_as_prose`
  - `swarm::tests::a_backslash_before_a_quote_and_delimiter_closes_the_quote_for_the_whole_line`
- **Resolution:** This defect was fixed twice, independently. This audit rewrote the scanner so quotes open only where an argument can start; a peer session, working the same tree at the same time, landed its own repair (`ee21f1b` and the apostrophe guard) built on the same rule plus a stricter one — a quote opens only when a matching close quote still exists later in the line, which prevents the unterminated-quote misparse outright instead of recovering from it. When the push raced and this commit was rebased onto the peer's seventeen, the peer's scanner won the conflict on merit and this audit's four regression tests were kept; all four pass against it.
  The reconciliation then surfaced what neither session had seen: `parse_delegations` runs **two** scanners over the same text, and only the first had been fixed — twice. `split_top_level_fields_limited`, which splits the accepted argument text into fields, still opened a quote at any field start, closable or not, and still read every `\"` as an escape. So `delegate_task(worker, "it's fine)` passed the repaired `action_argument` and was then dropped by the splitter's unterminated-quote check, one call later, with the same silence as before; and `delegate_task("dir\", "step 1) go")` came apart because the splitter escaped the quote the scanner had closed. The splitter now carries the same three quote rules as `action_argument` — argument-start opening, closability before opening, and the first-field close rule for `\"` — with a doc comment saying why the two grammars must never diverge again. The two tests above whose names describe prose and delimiters are the witnesses: both were watched failing against the merged tree before the splitter was patched.

### 2.2 `src/orchestrator.rs`: Windows discovery preferred the unspawnable npm shim (Tier 2)

- **Introduced by:** `3c4818a` — ironically, the commit that added `PATHEXT` support so Windows discovery would work at all.
- **Defect:** `which_on_path_in` checked the bare name before the `PATHEXT` candidates, and `is_executable_file` on Windows is only an `is_file()` check. npm — the usual way `claude` and its peers land on a Windows PATH — installs an extensionless POSIX `claude` script (for Git Bash) right next to `claude.cmd`, so discovery returned the sh script, which `CreateProcess` rejects (os error 193) on every spawn. The npm-installed CLI transport never worked on Windows.
- **Proof Test:** `cli_discovery_test::which_on_path_prefers_pathext_match_over_extensionless_npm_shim_on_windows`
- **Resolution:** `PATHEXT` candidates are tried before the bare name in each directory. The bare name stays as a last resort rather than being dropped: `CreateProcess` judges by PE format, not extension, so a genuinely extensionless executable still resolves when nothing shadows it.

### 2.3 `src/providers/mod.rs`: unbounded server-controlled rate-limit strings (Tier 3)

- **Surface widened by:** `55c528d` — `RateLimit::from_headers` had kept values verbatim since it was written, but the statusline feature started re-rendering them on every draw; they already flowed into every model's system prompt via the ledger's resource-budget section (bounded there only by the section-level `RESOURCE_BUDGETS_MAX_CHARS` cap).
- **Defect:** Header values are server-controlled text — a hostile or buggy endpoint (custom OpenAI-compatible endpoints are a supported configuration) could stuff kilobytes, or the one control byte `HeaderValue::to_str` admits (`\t`), into strings the codebase's own convention says must be bounded (`truncate_error_detail`, and `bae78fc`'s `record_file_list` fix for exactly this class).
- **Proof Test:** `providers::tests::rate_limit_header_values_are_bounded_and_control_character_free`
- **Resolution:** Each kept value passes through `bound_rate_limit_value`: control characters stripped (same rationale as `sanitize_progress_detail`), then capped at `MAX_RATE_LIMIT_VALUE_CHARS` (40 — a legitimate value is a short number, duration, or RFC 3339 timestamp) with the truncation announced by an ellipsis.

### 2.4 `tests/dependency_audit/*.ps1`: audits that pass when their tool fails (Tier 3)

- **Introduced by:** `3c4818a`.
- **Defect:** `$ErrorActionPreference = 'Stop'` does not apply to native commands. If `cargo tree -d --locked` exited nonzero, `$tree` was empty: the crossterm script saw zero duplicate versions and the windows-sys script saw no `0.59.0` match — both printed `OK` and the CI step stayed green with the audit never performed. GitHub's appended `exit $LASTEXITCODE` only reflects the *last* native command across all scripts, so an early failure was masked by a later success.
- **Proof:** The guard pattern was demonstrated to throw on a failing `cargo tree` invocation (exit 1), and all three scripts still pass on the healthy tree.
- **Resolution:** Both scripts now check `$LASTEXITCODE` immediately after `cargo tree` and throw, with a comment naming the PowerShell semantics that make the guard necessary.

### 2.5 The peer tree arrived red on Windows — and behind the red gate, a broken feature (Tier 2, upstream)

- **Introduced by:** the peer session's command-runner and probe commits, part of the seventeen that landed mid-audit. The peer works on Linux; none of this was visible there.
- **Defects, from the gate inward.** `cargo clippy --all-targets -- -D warnings` failed first: the test module's `generous_quota()` helper is consumed only by `#[cfg(unix)]` executor tests and carried no gate of its own, so on Windows it is dead code. Past clippy, three tests failed, and the deepest failure was not a test problem at all. `execute_command` builds its child environment from `env_clear()` — the right zero-trust posture — but on Windows that also scrubbed `ProgramFiles(x86)`, `SystemRoot`, `ComSpec`, and their siblings, through which rustc locates the MSVC linker (vswhere, the registry via COM) and Windows creates processes at all. Every `cargo test` inside a task copy — the entire proof-run protocol, in production, not just the test — died with ``linker `link.exe` not found`` before the fixture's own tests ever ran. The workflow test only saw it on the second run because its first assertion accepts any nonzero exit: infrastructure failure and honest red are indistinguishable at that assertion. Beside it, the rustup fallback read `HOME` — usually unset on Windows — so with the child's `USERPROFILE` redirected to the scratch runtime, a rustup proxy would hunt for toolchains in the scratch directory and find nothing (reproduced empirically: exit 1, "rustup could not choose a version of cargo"). The probe error mapping tested `is_timeout()` before `is_connect()`, and on Windows a refused loopback port is retried by the socket stack long enough to trip the 2-second connect timeout — a connect timeout satisfies both predicates — so an endpoint that was simply not there reported "authentication probe timed out". And the command-runner test asserted the resolved program's basename is exactly `cargo`, where Windows resolution legitimately appends a `PATHEXT` extension in that entry's case: `cargo.EXE`.
- **Proof:** the gate itself, all four ways — clippy's `dead_code` error, and the three test failures, each reproduced solo before the fixes and green after (the failing regions were byte-identical to the peer's push; nothing in this audit's changes touched them): `command_runner::tests::permits_cargo_test_and_rejects_shells_and_dangerous_subcommands`, `orchestrator::tests::automatic_workflow_reruns_red_and_green_in_one_copy_then_applies_it`, `orchestrator::tests::probe_network_failure_returns_unreachable`. The environment fix was additionally verified outside the harness: a faithful replication of the child environment fails `cargo test` on a healthy fixture without the system variables and passes with them.
- **Resolution:** The helper is `#[cfg(unix)]` like its consumers. `execute_command` passes through the Windows system-installation variables — machine-wide install locations, not user data, so nothing secret rides along — and resolves the rustup fallback from `HOME` or `USERPROFILE`, the parent's real home, before the child's is redirected. The probe mapping tests `is_connect()` first, with a comment fixing the semantics: "unreachable" is for handshakes that never completed, "timed out" for endpoints that accepted and went silent. The basename assertion compares the file stem case-insensitively.

### 4.1 What the mutation sweep found in this audit's own fixes

The first sweep — run against this audit's original scanner, before the rebase
told in §2.1 — came back **30 mutants: 28 caught, 1 unviable, 1 missed** —
`||` → `&&` in the escaped-quote delimiter heuristic. The survivor was not
equivalent, but it *was* masked: that scanner carried a quote-blind fallback
rescan that rescued exactly the inputs the pre-existing backslash tests use,
because for `("src\")`-shaped lines a scan that misreads the close as an escape
ends inside a quote, falls back, and lands on the same closing paren anyway.
The heuristic's failure only becomes observable when a **later quoted argument
contains a parenthesis** — `delegate_task("dir\", "step 1) go")` — where the
misread leaves the scanner inside the first quote, the second argument's
opening quote reads as the first one's close, and the `)` inside the prompt
ends the call early with a truncated prompt no fallback can repair.

That input became
`swarm::tests::a_backslash_before_a_quote_and_delimiter_closes_the_quote_for_the_whole_line`,
checked the project's usual way: the mutant was applied by hand and the test
went red. The fallback it outlived is gone — the merged scanner prevents the
misparse instead of recovering from it — but the test carried over intact, and
in the merged tree it pins the first-argument close rule in **both** scanners,
which is how it caught the splitter divergence of §2.1. The sweep over the
final merged diff — the reconciled scanner and splitter, the discovery and
header fixes, and finding 5's environment and probe repairs: **34 mutants
tested in 16m: 30 caught, 4 unviable, 0 missed**.
